# 凭据攻击

## 什么时候该用它

你发现了认证入口（HTTP 基本认证/表单登录、FTP、Redis、Telnet），并且想回答"这些账号
能不能用常见口令进去"。这是一次**会改变目标状态**的动作：连续失败可能触发账号锁定、
封禁或告警。所以先说清楚代价，再动。

## 平台自己实现的六个驱动，各自的判据

```
test_credentials target=10.0.0.5:8080 driver=http-basic accounts=["admin"] passwords=["admin","123456"]
test_credentials target=10.0.0.5:8080 driver=http-form accounts=["admin"] options={"success":"欢迎","failure":"密码错误","path":"/login","account_field":"user","password_field":"pass"}
test_credentials target=10.0.0.5 driver=ftp accounts=["anonymous"]
test_credentials target=10.0.0.5:6379 driver=redis
test_credentials target=10.0.0.5 driver=telnet options={"success":"#"}
```

| 驱动 | 默认端口 | 判据 | 必须由你提供的参数 |
|---|---|---|---|
| `http-basic` | 80 | **三个正向条件同时成立** | 无（`options.path` 可选） |
| `http-digest` | 80 | 先取 challenge 再算摘要（RFC 2617） | 无 |
| `http-form` | 80 | 成功/失败正则 | **`options.success` 与 `options.failure`** |
| `ftp` | 21 | 协议应答码（标准库 `ftplib`） | 无 |
| `redis` | 6379 | `AUTH` 应答 | 无 |
| `telnet` | 23 | 启发式：成功正则 | **`options.success`** |

**`http-form` 不给正则会被直接拒绝执行**，理由是："猜出来的成功是假凭据"。同理 `telnet`
在不同设备上提示串差别很大，必须由你给出"什么算进去"。

`http-basic` 的三个条件值得单独记住，因为它挡的是本类工具最经典的一类假凭据：

1. 状态码不是 401/407，且响应里**没有** `WWW-Authenticate`（有它就是还在要凭据）；
2. 正文里没有形似限流/锁定/验证码的措辞；
3. **差分**：不带凭据的基线响应与带凭据的响应**必须不同**。

第 3 条挡的是"这个入口本来就不需要认证"——那种情况下每个口令都会"成功"。实测里一个
"账号已锁定"的限流页会被朴素判定读成一次成功登录，然后报告上出现一个并不存在的有效凭据，
而操作员会拿着它去试其它系统。

**Redis 的 `AUTH` 被拒要读准**：那说明"服务没有认证"，比口令错严重得多，结果里单独标注。

## 锁定检测怎么工作

执行侧有一个 `LockoutGuard`，它**不**试图判断"目标是不是真的锁了"（那需要目标的内部状态，
看不到），它只判断"**目标对我的回应发生了我无法解释的变化**"，然后停在该账号并把理由写进结果。

判据是**失败签名的突变**：每次失败的响应会被归一化成签名（状态码 + 长度档 + 归一化正文的
哈希），抹掉时间戳、请求 id、计数、随机 token。第一次见到某个签名时，如果正文命中形似
限流/锁定的措辞（`locked`、`too many`、`captcha`、`验证码`、`次数过多`……）或者状态码是
429，就判定突变并停机。

**"第一次就遇到限流页"不算突变**——那说明目标对我们这台机器本来就有策略，不是我们打出来的。
这个区分写在 `seen` 的非空判断里。

配套的速率约束：每账号最多 5 次尝试、两次之间至少 250 ms（带 ±25% 抖动）、疑似锁定后冷却
30 秒；单次任务最多 32 个账号、64 个口令。抖动不是"为了隐蔽"，是因为被风控识别之后目标就
开始拒绝回应，观测就没了。

**停机时不要把"没试到"说成"不存在"**：报出 `stopped` 里的原话，它只说清是哪几条没试。

## SSH / SMB / RDP / WinRM 在常见部署上是断的

本平台**没有**这四个协议的原生驱动。原因不是不想做：手写的协议实现会在更新的服务端上
**静默产生假阴性**——而假阴性比"没有这个能力"坏得多，它会让使用者把这台机器从范围里划掉。

这条路只能交给外部客户端（SSH → ncrack/hydra，SMB → netexec/smbclient，RDP → ncrack/hydra，
WinRM → evil-winrm/netexec）。而这些客户端**在 Windows 上没有免安装构建**，本平台也不会替你
去调系统包管理器（那正是"装进项目目录"要避免的事）：

- ncrack：nmap.org 只发 `-setup.exe`，没有 zip；
- hydra：上游不发 Windows 构建；PyPI 上的 `hydra` 是 Facebook Research 的配置框架，**与口令
  测试无关**，接上去会让 `-l/-P` 落到一个完全不同的程序里；
- smbclient：Windows 上没有免安装构建；pip 上的 `impacket` 有个同名脚本但命令行完全不同；
- netexec：不是单文件工具，`pipx install git+…` 会连带装一整套依赖；
- evil-winrm：Ruby gem，PyPI 上没有同名包（实测 404），需要先有 Ruby 运行时。

所以**先在 `list_toolkit` 里看**：这四项里能自动安装的是**零个**。一个纯 Windows 单节点
部署上，这四个协议就是**测不了**的。

**平台自己会把这件事一次说完**：不带 `driver` 调一次 `test_credentials`，失败信息里
就带着每个被委派协议、各自的客户端、以及客户端装没装。照那段话向使用者交代，
不要自己另编一套。**断开的闭环要如实交代**，
不要说"请换个参数"，也不要说"去 list_toolkit 看看"——`list_toolkit` 会把人推回手工安装，
手工安装不属平台能力，三条路的尽头互相指着对方，没有一条说"这条是断的"。正确的说法是：

> SSH 口令测试在这台节点上做不了：平台没有 SSH 的原生驱动（手写实现会静默产生假阴性），
> 可用的客户端 ncrack 与 hydra 在 Windows 上没有免安装构建，平台也不能替你装。两条出路：
> 在一台已装这些客户端的机器上注册一个执行节点，或者先用 `run_tool adapter=ssh` 做单次
> 登录验证（那是 pivot 类，不是字典攻击）。

## 口令去哪了

结果里**带回找到的口令本体**（操作员要拿它登进去），但链路节点里只写
`authz.fingerprint()`——链路会被导出、会被翻看、会进报告，口令写进去就收不回来了。
这也意味着：**报告里对不上口令原文是正常的**，要看原文得读任务结果（`get_job`）。

## 代价与边界

- 本部署 `authz.FORCE_OPEN=True`：五类侵入动作的准入判定不参与判定，**不要**让用户去配
  `--allow-intrusive`；仍然生效的是探测作用域与权限档（默认都放开）。
- 权限档不解锁侵入动作那条设计没变：档位不到连 `test_credentials` 这个工具都看不到。
- 字典是操作员的输入，不是能力。内置那几组（`admin/admin`、`root/root` 一类）只是"省得为了
  试一个最常见的组合先去找字典"；字典一大，账号数/口令数上限会更早生效。
- 一次凭据测试可能触发真实的账号锁定。要在汇报里写明"试了哪些账号、几次、有没有触发停机"。
