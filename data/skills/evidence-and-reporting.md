# 证据读取与交付

## 什么时候该用它

任何一个"我要把结论说给别人听"的时刻。这个平台的每一条结论都挂着一次具体观测，而读取那
次观测的方式与读一屏状态不同——**它们是分页的**。这一份讲的就是怎么读全、读不到时怎么说。

## 链路里有四种节点，别混

| 类型 | 是什么 | 典型内容 |
|---|---|---|
| `intent` **意图** | 打算做什么 | "审计认证与文件上传逻辑" |
| `fact` **事实** | 观测到了什么 | banner、端口、TLS 版本、nmap 原始输出的出处（`jobId`） |
| `asset` **资产** | 有什么东西 | 根域/子域/IP/服务/应用/端点 |
| `finding` **交付项** | 可判定的缺陷 | 标题、严重度、受影响资产、可复现步骤 |

**`fact` 与 `finding` 的区别是本平台最要紧的一条纪律**：端口开放、"经跳板可达"、"nmap 跑完
退出码 0"都只是**事实**，不是缺陷。所以报告里的交付项少，不等于工作做得少——恰恰相反，
把事实硬升成交付项会让报告里出现一批没有影响说明的高危。汇报时把两类分开写。

**只有 `verified` 的利用验证会生成交付项。** 静态命中（`confirmed_static`）与未判定
（`inconclusive`）都不生成——前者需要人复核，后者不是"否"。

## 读取口与它们的分页

```
get_chain_overview          # 只有最近若干节点的**标题**，先看规模
get_chain_nodes kind=fact limit=40
get_chain_nodes kind=finding limit=40
get_chain_nodes nodeId=fact-70          # 只要那一条
get_findings severity=high limit=100
get_assets limit=100
get_report                              # 整篇报告
get_report jobId=job-xxxxxxxx           # 那一次任务的作业报告
get_job jobId=job-xxxxxxxx              # 任务的原始结果（含外部工具输出）
list_jobs status=done limit=20
```

四套信封，键名统一，学一次就够：

| 读取口 | 默认 | 上限 | 单位 |
|---|---|---|---|
| `get_report` / `get_job` | 6000 字符 | 24000 | **字符** |
| `get_findings` / `get_assets` / `list_jobs` | 20 条 | 100 | **条** |
| `get_chain_nodes` | 40 个节点 | 200 | **节点** |

三者都返回 `total` / `count` / `limit` / `offset` / `nextOffset` / `hasMore`（`truncated`
是 `hasMore` 的同义别名，两键永远同值）。**`nextOffset` 就是下一页该从哪儿开始**——不给它
的话每一次翻页都要自己做加法，而算错 offset 的表现是**静默跳过一段正文**：读的人不会发现，
他看到的仍然是一份通顺的报告。

`list_jobs` 的窗口从**最新**那条往回数（0 就是最新那批），所以"查进展"不需要先知道总数。
`get_chain_nodes` 的分页按**节点**而不是按字符；单个节点正文有长度上限（4000 字符），
被裁过的条目会标出来。

## 报告是**文档**，界面是窗口

`store.report_markdown` 的 `limit` 参数决定这件事：**`limit=None` 出完整文档，不截节点窗口**。
界面走默认窗口（200 个节点的图铺不开，而且它自己会印一行"另有 N 条未在图中展示"）；
而 `get_report` 工具与导出走完整文档。

所以**不要拿界面看到的当报告**：界面上少的那部分是有意省掉的，不是不存在。反过来，
`get_report` 返回几千到上万字符，要按字符翻页读到底。

**`jobId` 不是过滤器，是换一篇文档。** 作业报告有它自己的执行信息、自己的失败原因、自己的
"本次没有向链路写入任何节点"。做成"汇总报告过滤一下"会得到一篇没有主语的文章：读者分不出
这是"这次什么都没发现"，还是"上次发现的东西这次被过滤掉了"——而这两种情况要采取的行动完全
相反。报告里的时间**一律是绝对时间**（`YYYY-MM-DD HH:MM:SS`），不写"3 分钟前"：报告要归档、
要贴进工单、要跟别人的日志对时间，相对时间放进附件之后每一秒都在变得更错。

## 原始输出在哪

`run_tool` 跑完，链路里那条事实只记着"退出码 0，输出 1235 字节"——**真正的输出在任务里**：

```
get_chain_nodes kind=fact limit=40        # 找到那条事实，记下它的 jobId
get_job jobId=job-xxxxxxxx                # 第一页
get_job jobId=job-xxxxxxxx offset=6000    # 带 nextOffset 继续，直到 hasMore 为 false
```

外部工具输出会被**打码**（凭据、hash、ticket）并截断到 256 KB；被截断时任务 summary 的
`degraded` 里会写"输出已截断"。同理，探测没扫完会写"未完成的部分未计入结论"，nmap 缺
Npcap 会写"已退回 connect() 模式"。

## "读不全"该怎么如实说明

这是这一份最实用的一段。三类情况，三种说法：

1. **有 `hasMore` 为 true 而你没继续读** → "我读了前 N 条/前 N 个字符，共 M 条/M 字符，
   还有未读部分"。不要用第一页的条数当总数。
2. **任务 summary 里有 `degraded`** → 原样转述那几句，并说明它影响哪一部分结论。
   `degraded` 为空才是"这一份是完整的"。
3. **读取口本身返回空** → 先确认 engagement 选对了（省略 `engagementId` 时取的是**最近创建**
   的那个），再确认任务是不是还没执行完（工具都是后台的，下发立刻返回作业号）。
   不要把它说成"没有问题"。

一条通用的写法：**结论 = 观测 + 覆盖范围**。例如"在本次覆盖的 3 个地址、30 个端口下，
Redis 未授权 1 处（10.0.0.9:6379，`PING` 返回 PONG）；另有 2 个端口探测未完成"。这句话可以
被复核；而"目标存在 Redis 未授权漏洞"不能。

## 交付

`clear_finished_jobs` 清的是**任务记录**，不是证据：链路、漏洞与报告都挂在 engagement 上，
不受影响。所以清队列是安全的操作，但它也**不会**让报告变小。
`kill_job` 的语义是"这次执行的结果作废"，不是"立刻掐断那个进程"——running 的记录被删掉
后，节点跑完回传时查不到这条任务，结果会被丢弃、不会写进链路。
